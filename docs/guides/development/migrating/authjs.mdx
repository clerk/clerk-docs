This guide shows how to migrate an application using Auth.js (formerly NextAuth.js) to use Clerk for authentication.

<Steps>
  ## Install `@clerk/nextjs`

  Clerk's Next.js SDK gives you access to prebuilt [components](/docs/reference/components/overview), [hooks](/docs/reference/nextjs/overview#client-side-helpers), and [helpers](/docs/reference/nextjs/overview) for Next.js Server Components, Route Handlers and Middleware. Run the following command to install it:

  ```npm
  npm install @clerk/nextjs
  ```

  ## Set environment variables

  Add the following code to your `.env` file to set your [Publishable Key](!publishable-key) and [Secret Key](!secret-key).

  ```env {{ filename: '.env' }}
  NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY={{pub_key}}
  CLERK_SECRET_KEY={{secret}}
  ```

  ## Wrap your Next.js app in `<ClerkProvider>`

  Remove the `<SessionProvider session={session}>` provider from Auth.js and replace it with `<ClerkProvider>`.

  <Include src="_partials/clerk-provider/explanation" />

  <CodeBlockTabs options={["App Router", "Pages Router"]}>
    ```tsx {{ filename: 'app/layout.tsx', mark: [1, 8] }}
    import { ClerkProvider } from '@clerk/nextjs'
    import './globals.css'

    export default function RootLayout({ children }: { children: React.ReactNode }) {
      return (
        <html lang="en">
          <body>
            <ClerkProvider>{children}</ClerkProvider>
          </body>
        </html>
      )
    }
    ```

    ```tsx {{ filename: 'pages/_app.tsx', mark: [2, 6, 8] }}
    import '@/styles/globals.css'
    import { ClerkProvider } from '@clerk/nextjs'
    import type { AppProps } from 'next/app'
    function MyApp({ Component, pageProps }: AppProps) {
      return (
        <ClerkProvider {...pageProps}>
          <Component {...pageProps} />
        </ClerkProvider>
      )
    }
    export default MyApp
    ```
  </CodeBlockTabs>

  ## Set up sign-up and sign-in UI

  ### Account Portal

  Clerk's Account Portal hosts the `<SignIn />`, `<SignUp />`, `<UserProfile />`, and other components for your application. Read more about [Account Portal](/docs/guides/account-portal/overview).

  To use the Account Portal, remove the routes that mount the Auth.js sign-in and sign-up UI. Replace the links to those routes with the [`<SignInButton>`](/docs/reference/components/unstyled/sign-in-button) or [`<SignUpButton>`](/docs/reference/components/unstyled/sign-up-button) components.

  ### Self-hosted UI

  If Clerk's Account Portal pages aren't a good fit for your app, you can build a custom sign-in and sign-up UI in one of two ways:

  - use the [prebuilt components](/docs/guides/development/custom-sign-in-or-up-page), such as the [`<SignIn />`](/docs/reference/components/authentication/sign-in) and [`<SignUp />`](/docs/reference/components/authentication/sign-up) components
  - build a [fully custom UI using the Clerk API](/docs/guides/development/custom-flows/overview) with Clerk's React hooks, such as [`useSignIn()`](/docs/reference/hooks/use-sign-in) and [`useSignUp()`](/docs/reference/hooks/use-sign-up)

  ## Protect your app

  You can control access in two ways: protect your whole app or specific routes with Clerk Middleware, or show and hide UI with Clerk's components based on whether the user is signed in.

  ### Control access to your app with Clerk Middleware

  You will need to remove the Auth.js Middleware from your application, and replace it with Clerk's Middleware helper, `clerkMiddleware()`.

  Auth.js's middleware always rejects unauthorized requests. You may have additionally configured the Next.js middleware config to protect specific private routes. You will need to make note of this configuration so you can recreate it.

  By default, Clerk's Middleware runs for your entire application.

  The example below is a basic configuration that does not protect any routes. All routes are public and you must opt-in to protection for routes. Read the [`clerkMiddleware()`](/docs/reference/nextjs/clerk-middleware) documentation to learn more about how you can configure your Middleware.

  <Include src="_partials/nextjs/nextjs-15-callout" />

  ```tsx {{ filename: 'proxy.ts' }}
  import { clerkMiddleware } from '@clerk/nextjs/server'

  export default clerkMiddleware()

  export const config = {
    matcher: [
      '/((?!.*\\..*|_next).*)', // Don't run middleware on static files
      '/', // Run middleware on index page
      '/(api|trpc)(.*)', // Run middleware on API routes
      '/__clerk/(.*)', // Run middleware on Clerk frontend API routes
    ],
  }
  ```

  ### Control access to your app with Clerk's components

  To conditionally render UI when the user is signed in, wrap it with [`<Show when="signed-in">`](/docs/reference/components/control/show).

  To conditionally render UI when the user is _not_ signed in, wrap it with [`<Show when="signed-out">`](/docs/reference/components/control/show).

  ```tsx {{ filename: 'app/page.tsx' }}
  import { Show } from '@clerk/nextjs'
  import { Suspense } from 'react'

  export default function Home() {
    return (
      <div>
        <Suspense>
          <Show when="signed-out">
            <p>This content is public. Only signed out users can see this.</p>
          </Show>
          <Show when="signed-in">
            <p>This content is private. Only signed in users can see this.</p>
          </Show>
        </Suspense>
      </div>
    )
  }
  ```

  ## Read user and session data

  ### Server-side

  Replace any Auth.js `getServerSession(req, res, authOptions)` with Clerk's helpers.

  <Tabs items={["App Router", "Pages Router"]}>
    <Tab>
      Replace Auth.js's `getServerSession()` with Clerk's [`auth()`](/docs/reference/nextjs/app-router/auth) helper to read your user data.

      ```tsx {{ filename: 'app/page.tsx' }}
      import { auth } from '@clerk/nextjs/server'
      import { Suspense } from 'react'

      export default function Page() {
        return (
          <Suspense>
            <Home />
          </Suspense>
        )
      }

      async function Home() {
        const { userId } = await auth()
        console.log(userId)

        return <p>Home Page</p>
      }
      ```
    </Tab>

    <Tab>
      Replace Auth.js's `getServerSession()` with Clerk's [`getAuth()`](/docs/reference/nextjs/pages-router/get-auth) helper to read your user data.

      ```tsx {{ filename: 'pages/index.tsx' }}
      import { getAuth, buildClerkProps } from '@clerk/nextjs/server'
      import { GetServerSideProps } from 'next'

      export const getServerSideProps: GetServerSideProps = async (ctx) => {
        const { userId } = getAuth(ctx.req)
        console.log(userId)

        return { props: { ...buildClerkProps(ctx.req) } }
      }
      ```
    </Tab>
  </Tabs>

  ### Client-side

  Replace Auth.js's `useSession()` hook with Clerk's hooks.

  The [`useAuth()`](/docs/reference/hooks/use-auth) hook can be used to retrieve basic authentication information. The [`useUser()`](/docs/reference/hooks/use-user) hook can be used to retrieve the full [`User`](/docs/reference/objects/user) object, which includes information about the user, such as their first name, emails, phone numbers, and more.

  ```tsx {{ filename: 'app/page.tsx' }}
  'use client'
  import { useAuth, useUser } from '@clerk/nextjs'

  export default function Home() {
    const { userId, sessionId } = useAuth()
    const { isSignedIn, user } = useUser()
    console.log(userId, sessionId, isSignedIn, user)

    return <p>Home Page</p>
  }
  ```

  ## User IDs as foreign keys

  If your database uses the Auth.js `userId` as a foreign key, you have two options:

  - [Use Clerk's `externalId` field](#use-clerks-externalid-field)
  - [Update your Auth.js database](#update-your-database)

  ### Use Clerk's `externalId` field

  When you migrate user data from Auth.js to Clerk, Clerk generates new user IDs for each user. If you are using existing user IDs as foreign keys in your database (e.g., in a `user_id` column), you can save those IDs as the user's `externalId` in Clerk. This `externalId` can be included in the [session token](!session-token) by adding the following [customization](/docs/guides/sessions/customize-session-tokens). The following example will set the user's ID to be `externalId` if one is present, otherwise, it will use the Clerk's user ID.

  ```json
  {
    "userId": "{{user.external_id || user.id}}"
  }
  ```

  <Tabs items={["App Router", "Pages Router"]}>
    <Tab>
      To access the `userId` from the session claims, you can use the `auth()` helper.

      ```tsx {{ filename: 'app/page.tsx' }}
      import { auth } from '@clerk/nextjs/server'
      import { Suspense } from 'react'

      export default function Page() {
        return (
          <Suspense>
            <Welcome />
          </Suspense>
        )
      }

      async function Welcome() {
        const { sessionClaims } = await auth()

        if (!sessionClaims) {
          return <p>Not signed in</p>
        }

        const userId = sessionClaims.userId

        return <p>Welcome user {userId}</p>
      }
      ```
    </Tab>

    <Tab>
      To access the `userId` from the session claims, you can use the `getAuth()` helper.

      ```tsx {{ filename: 'pages/index.tsx' }}
      import { getAuth, buildClerkProps } from '@clerk/nextjs/server'
      import { GetServerSideProps } from 'next'

      export const getServerSideProps: GetServerSideProps = async (ctx) => {
        const { isAuthenticated, sessionClaims } = getAuth(ctx.req)

        if (!isAuthenticated) {
          return { props: { ...buildClerkProps(ctx.req) } }
        }

        const userId = sessionClaims.userId
        console.log(userId)

        return { props: { ...buildClerkProps(ctx.req) } }
      }
      ```
    </Tab>
  </Tabs>

  > [!NOTE]
  > You can't read this claim on the client. If you use one of Clerk's hooks, check whether `externalId` exists. If it doesn't, read `userId`.

  ### Update your database

  After the data migration, update the foreign keys in your database to the new Clerk user IDs if you prefer to replace the Auth.js IDs.

  To keep referencing users by their existing IDs, see [foreign keys](/docs/guides/development/migrating/plan-your-migration#foreign-keys).

  ## Create a Clerk production instance

  Every Clerk application has a `Development` and a `Production` instance. Before you start migrating user data, you need to configure your Clerk `Production` instance and migrate your Auth.js users directly into that instance. The [Deploying to Production](/docs/guides/development/deployment/production) page covers creating a `Production` instance.

  To test the migration or set up staging, import a small set of users into the `Development` instance first.

  ## Migrate user data from Auth.js to Clerk

  The [Clerk CLI](/docs/cli) exports your users from your Auth.js database with `clerk migrate export authjs`, then creates them in Clerk with `clerk migrate import`.

  To retain the user data in your database for easy querying, see the [guide on data synchronization with webhooks](/docs/guides/development/webhooks/syncing).

  ### What migrates

  - **Auth.js IDs:** Each user's `id` becomes the Clerk user's `external_id`.
  - **Names:** `name` becomes `firstName` and `lastName`. The source uses a one-word name as the first name, unless it matches the user's own email address. In that case, the source omits it.
  - **Unverified emails:** They stay unverified by default. Auth.js records email verification as a nullable timestamp. The import attaches an address with no `emailVerified` value as unverified and keeps it off the primary fields. The checks reject a user whose only email is unverified when your instance requires an email. Auth.js leaves an OAuth user's email unverified, and the export warns when it finds any. If every provider you use verifies addresses, pass `--trust-oauth-emails` to the export to mark those emails verified. To reserve unverified addresses instead, see [unverified emails and phones](/docs/guides/development/migrating/how-the-cli-migrates-users#unverified-emails-and-phones).

  ### What doesn't migrate

  - **Passwords:** Auth.js core stores no passwords. Its users sign in with OAuth or email links, so they arrive without credentials.

    If your app also uses the Credentials provider, those passwords live in your app's own tables, and the export doesn't read them. Add them to the file yourself, as in [import a file you exported yourself](#import-a-file-you-exported-yourself), or have those users reset their password.

  - **Social accounts:** Enable the same providers on the [**SSO connections**](https://dashboard.clerk.com/~/user-authentication/sso-connections) page in the Clerk Dashboard. When a user signs in with one, Clerk links it to their imported account by verified email address. Clerk doesn't link to an address the import attached as unverified, so that sign-in creates a separate user. To link those users, import with `--reserve-unverified`. If you reserve the address and the provider doesn't confirm it, Clerk asks the user to verify it before linking. See [account linking](/docs/guides/configure/auth-strategies/social-connections/account-linking).

  ### Export your users from your Auth.js database

  Run the export, and enter your database's connection string when the CLI asks:

  ```sh {{ filename: 'terminal' }}
  clerk migrate export authjs
  ```

  Enter a Postgres, MySQL, or libsql/Turso connection string, such as `postgres://<user>:<password>@<host>:5432/<database>`. For libsql/Turso (`libsql://…`), include the token in `?authToken=` or set `TURSO_AUTH_TOKEN` or `LIBSQL_AUTH_TOKEN`.

  For SQLite, pass the file path with `--db-url`. The path has to start with `file:` or `./`, or end in `.sqlite`, `.sqlite3`, or `.db`.

  Without `--db-url`, the CLI reads `AUTHJS_DB_URL`, then prompts for it. The prompt masks what you type, and a value entered at a prompt stays out of your shell history. If the database rejects the connection string, the prompt explains why and asks again. With `--yes`, `--json`, in an agent run, or without a terminal, the export doesn't prompt, and fails if the connection string is missing or rejected.

  Prisma capitalizes the Auth.js user table, and Drizzle doesn't. The export tries `next_auth.users` (the Supabase adapter's table, on Postgres only), `User`, `user`, then `users`, and reports which table it found. It also reads the legacy NextAuth `email_verified` and `created_at` columns when that's the shape it finds.

  It saves your users as `export.json` in a new run, and prints the run ID and a field coverage table:

  ```text
  Field coverage
    ✓ 240/240 have an email address
    ! 198/240 have a verified email
    ! 176/240 have a name
  ```

  Pass `-o <path>` to write the file somewhere else. The path has to end in `.json`.

  ### Import your users into Clerk

  With `--app` or a linked project, the import targets development by default. For production, add `--instance prod` to the dry-run command and keep it when you import. With a Secret Key, use the production instance's key instead.

  ### Import a file you exported yourself

  To import users from an API response or database export, save them as `users.json` in the following format:

  ```json {{ filename: 'users.json' }}
  [
    {
      "userId": "string",
      "email": "email",
      "email_verified": "timestamp (optional)",
      "created_at": "timestamp (optional)",
      "firstName": "string (optional)",
      "lastName": "string (optional)",
      "password": "string (optional)",
      "passwordHasher": "string (required whenever password is set)"
    }
  ]
  ```

  Then run `clerk migrate import users.json --source authjs`.

  For the accepted `passwordHasher` values, see `password_hasher` in the [`CreateUser` Backend API reference](/docs/reference/backend-api/tag/users/POST/users){{ target: '_blank' }}. The CLI rejects unsupported `passwordHasher` values before importing users and lists the accepted values in the error. `email_verified` has to be a date or an epoch timestamp. Omit it, or set it to `0`, `true`, or a value that isn't a date, and the address is imported as an unverified email. Include `created_at` to keep each user's original signup date. An `id` field works in place of `userId`.

  The SQL below mirrors the query `clerk migrate export authjs` runs against Prisma's `User` table on Postgres, so both paths produce the same user fields. The export also reads the account table to find each user's OAuth providers and to apply `--trust-oauth-emails`, which this query skips. Substitute your own table name if your adapter didn't create `User`, such as `next_auth.users` for the Supabase adapter, and swap the double quotes for backticks on MySQL. On a legacy NextAuth table, select `email_verified` and `created_at` as they are.

  ```sql
  SELECT id, name, email, "emailVerified" AS email_verified FROM "User"
  ```

  ### Verify the migration

  1. Read what the run did. It lists the users that failed or were skipped, and why:

     ```sh {{ filename: 'terminal' }}
     clerk migrate runs <import_run_id>
     ```

  1. In the Clerk Dashboard, navigate to the [**Users**](https://dashboard.clerk.com/~/users) page and check that your users are listed. Run `clerk users list` to check from your terminal.

  1. Sign in to your Clerk-secured application with one of the migrated accounts.
