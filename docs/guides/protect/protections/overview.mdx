Protections are defenses that Clerk builds and maintains, and that you can turn on for your application. Each one targets a specific kind of abuse, such as password guessing or sign-ups from cloud servers.

## How protections work

- **Each protection applies to specific steps.** Some apply to sign-ups, some to sign-ins, and some to both. A few also apply when a user adds an email address. The **Applies to** column in [Available protections](#available-protections) shows which.
- **Each protection takes one kind of action.** Most block or challenge the attempt. Others lock the account, ask for a second factor, reject an email address, or limit how often something can be tried. The **Action** column shows which.
- **Most are off until you turn them on.** These are on by default: [Challenge suspicious sign-ups](/docs/guides/protect/bot-protection) and [Lock accounts after failed sign-ins](/docs/guides/protect/user-lockout) for new applications, [Device Trust](/docs/guides/protect/device-trust) for applications created after November 14, 2025, and [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence) for instances created on or after October 27, 2026. Bulk [user enumeration protection](/docs/guides/protect/user-enumeration-protection) is always on.
- **Clerk also rate-limits sign-up and sign-in requests on every plan.** Each IP address can only start so many sign-ups and sign-ins, and submit so many passwords and codes, in a short time. These limits aren't a protection you manage. See [Frontend API requests](/docs/guides/how-clerk-works/system-limits#frontend-api-requests).

## Protections that block or challenge

Protections whose action is **Block** or **Challenge** all work the way this section describes. For the other protections, each one's page explains when it applies and what the user sees.

### When protections check an attempt

- **Sign-ups**: most protections act as soon as a sign-up starts. [Block risky email domains](/docs/guides/protect/protections/block-risky-email-domains) acts when the email address is entered.
- **Sign-ins aren't checked.** These protections apply to sign-ups only, so they never stop existing users from signing in.
- **Users you create yourself aren't checked.** These protections don't apply to users you create with the [Backend API](/docs/reference/backend-api){{ target: '_blank' }}, in the Clerk Dashboard, or by importing them.
- **Automated tests aren't checked.** A sign-up that carries a valid [Testing Token](/docs/guides/development/testing/overview#testing-tokens) isn't checked by these protections, so end-to-end tests keep running.

### What blocked users see

When a protection blocks a sign-up, the attempt doesn't go through. What the user sees depends on where it's blocked and which versions of Clerk's SDKs your application runs:

- **Prebuilt components with `@clerk/ui` 1.36.0 or later and ClerkJS 6.34.1 or later** show a screen explaining that the user can't continue, with a reference code. Core 3 SDKs load the latest versions automatically. The screen appears when the attempt is blocked on the first step, or when the user returns from a social or SSO provider.
- **A block at a later step,** such as after the user enters a password or a verification code, shows a short error message instead of the full screen. So do older SDK versions.
- **In a [custom flow](!custom-flow),** the request fails with an error whose code is `action_blocked`. See [Error handling](/docs/guides/development/custom-flows/error-handling).

When a protection challenges an attempt instead, the user completes a verification step and then carries on.

### When more than one protection matches

If more than one protection matches the same attempt, a block applies before a challenge.

### Where decisions appear

Every block and challenge appears as a [Protect event](/docs/guides/dashboard/logs/application-logs#protect-events) in Application Logs, so you can see what a protection is doing once it's on.

### If you proxy Clerk's Frontend API

Several of these protections decide based on where an attempt comes from, so Protect needs each visitor's IP address. If you [proxy Clerk's Frontend API](/docs/guides/dashboard/dns-domains/proxy-fapi) through your own server, your proxy must send the visitor's IP address in the `X-Forwarded-For` header, as described in [Configure your proxy server](/docs/guides/dashboard/dns-domains/proxy-fapi#configure-your-proxy-server). Otherwise every attempt looks like it comes from your proxy, and those protections can block everyone or no one.

## Plans

Some protections are included on every plan, and others require the Business plan. Each protection's page lists what it requires. See [pricing](/pricing).

## Manage protections in the Dashboard

In the Clerk Dashboard, under **Protect**, navigate to the [**Protections**](https://dashboard.clerk.com/~/protect/protections) page. It lists the protections on your application, each with its **Status**. To enable a protection, change its settings, or disable it, select the settings icon at the end of its row. Without the [Business plan](/pricing), a protection that requires it shows a lock icon and no status, and its settings icon leads to the upgrade. To test protections before you enable them in production, see [Enable protections](/docs/guides/protect/getting-started#enable-protections).
