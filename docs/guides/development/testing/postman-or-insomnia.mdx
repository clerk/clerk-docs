Postman and Insomnia are powerful tools used to test API's, validate their behavior, and automate testing tasks. Basic testing with these tools is similar, and this guide will help you get started with either option.

## Generate a long-lived session token

> [!NOTE]
> This flow is intended for testing. Use it with your development instance, not your production instance.

The standard [session token](!session-token) issued by Clerk expires after 60 seconds. Clerk SDKs handle refreshing the token regularly so that the authentication state is kept up to date. Because this token expires quickly, it isn't very useful when trying to test with Postman or Insomnia.

Instead, use the Backend API to create a session token with a longer lifetime. This token is a regular session token, so it includes any custom claims you added to your session token and the session's [Active Organization](!active-organization), and it's accepted wherever your backend expects one.

> [!WARNING]
> Earlier versions of this guide used a token from a [JWT template](/docs/guides/sessions/jwt-templates). Starting in `@clerk/backend` 3.16.9, `authenticateRequest()` rejects JWT template tokens where a session token is expected, with the reason `token-type-mismatch`. If your requests started failing with this reason, replace your JWT template token with a session token from this guide.

### Get a session ID

Visit your frontend that is using the development instance of the Clerk application you want to test. Sign in as a user. The user that you sign in as will be the user you test with in Postman or Insomnia. Once you have signed in, open your Dev Tools and go to the **Console** tab. Enter the following command to get the ID of the current session:

```js
window.Clerk.session.id
```

Don't sign out of this session. The Backend API can only create tokens for an active session.

### Create the token

Call the [Create a session token endpoint](/docs/reference/backend-api/tag/sessions/POST/sessions/\{session_id}/tokens){{ target: '_blank' }} with the session ID. Set `expires_in_seconds` to how long the token should stay valid (minimum `30`). Prefer hours or days over months or years, because the token can't be revoked before it expires.

<SignedIn>
  - Your [Secret Key](!secret-key) is already injected into the code snippet.
  - Replace `sess_123` with the session ID you copied from the console.
</SignedIn>

<SignedOut>
  - Replace `YOUR_SECRET_KEY` with your Clerk [Secret Key](!secret-key).
  - Replace `sess_123` with the session ID you copied from the console.
</SignedOut>

```bash
curl 'https://api.clerk.com/v1/sessions/sess_123/tokens' \
  --request POST \
  --header 'Content-Type: application/json' \
  --header 'Authorization: Bearer {{secret}}' \
  --data '{
  "expires_in_seconds": 86400
}'
```

The token is returned in the `jwt` field of the response. Copy it to use in Postman or Insomnia. The token keeps the claims it had when it was created. If you switch the Active Organization or change your custom claims, create a new token and replace it in Postman or Insomnia.

You can also create the token from your backend with the JS Backend SDK's [`getToken()`](/docs/reference/backend/sessions/get-token) method by passing `undefined` as the template and the lifetime in seconds, for example `clerkClient.sessions.getToken('sess_123', undefined, 86400)`.

> [!WARNING]
> The token stays valid until it expires, even if the user signs out or the session is revoked. Keep the lifetime as short as your testing allows, and don't share the token.

## Using Postman or Insomnia

<Tabs items={["Postman", "Insomnia"]}>
  <Tab>
    Open Postman and create a new request.

    ![The Postman app with a red arrow pointing at the plus icon in the top-left corner](/docs/images/testing/postman-new-request.webp)

    Configure Postman with the method and URL for the API Route you want to test. This example uses the `POST` method and the `/api/protected-route` route.

    ![The Postman app with a red box around the method and URL field](/docs/images/testing/postman-configure-request.webp)

    Navigate to the **Authorization** tab and for token type, select **Bearer Token**. Paste the `jwt` value from the Backend API response as the Bearer Token. Your request will now authenticate as the user you created the token with.

    ![The Postman app with the first red arrow pointing at the Authorization tab, the second red arrow pointing at the token type with 'Bearer token' chosen, and a third red arrow pointing at the token field with the token pasted in](/docs/images/testing/postman-bearer-token.webp)

  <Tab>

    ![The Insomnia app with a red arrow pointing at the 'New HTTP Request' button](/docs/images/testing/insomnia-new-request.webp)

    Configure Insomnia with the method and URL for the API Route you want to test. This example uses the `POST` method and the `/api/protected-route` route.

    Navigate to the **Auth** tab and select **Auth** again to show a menu of auth types. Choose the **Bearer token** option. Paste the `jwt` value from the Backend API response. Your request will now authenticate as the user you created the token with.

## Grouping requests

Postman and Insomnia both provide a **Collections** feature, which allows you to group requests together. Inside that collection, you can add **[Variables](https://learning.postman.com/docs/sending-requests/variables/)** (Postman) or **[Environment Variables](https://docs.insomnia.rest/insomnia/environment-variables)** (Insomnia). These features enable you to use a single token across multiple requests and also allow you to store tokens for multiple users. This is great for testing different features in your application by conveniently changing the token/user you are testing with. You can read more in [Postman's Variables documentation](https://learning.postman.com/docs/sending-requests/variables/) and [Insomnia's Environment Variables documentation](https://docs.insomnia.rest/insomnia/environment-variables).
