---
title: Migrate to Clerk
description: Guides on how to move your user data from another authentication platform to Clerk.
---

Move your users to Clerk from the platform you use today, and keep their passwords when your platform exports them. The [Clerk CLI](/docs/cli) exports your users, checks each one against your Clerk instance before it writes anything, and imports them. If something goes wrong, it can undo the import.

## Supported platforms

- [Auth0](/docs/guides/development/migrating/auth0)
- [Auth.js (NextAuth)](/docs/guides/development/migrating/authjs)
- [Better Auth](/docs/guides/development/migrating/better-auth)
- [Firebase](/docs/guides/development/migrating/firebase)
- [Supabase](/docs/guides/development/migrating/supabase)
- [WorkOS](/docs/guides/development/migrating/workos)
- [Another Clerk instance](/docs/guides/development/migrating/clerk-to-clerk), such as development to production. A production instance starts empty.
- [AWS Cognito](/docs/guides/development/migrating/cognito), which uses a password migrator instead of `clerk migrate`.
- [Another platform](/docs/guides/development/migrating/custom-source), by writing a source that maps its export onto Clerk's user schema.

Better Auth, Firebase, and Supabase exports keep password hashes, so most of those users sign in with the passwords they already have. Auth0 releases hashes only through a support request. Auth.js and WorkOS users, and users copied with `clerk migrate export clerk`, reset their password or sign in another way. Each guide lists the exceptions.

## Choose an approach

Most migrations import every user at once, which is what `clerk migrate` does. A trickle migration moves them over time while both systems run, and you build that import yourself with the Backend API. [Plan your migration](/docs/guides/development/migrating/plan-your-migration) covers the trade-offs of each, and how your app keeps referencing users by the IDs they had before.

## Run your migration

<Include src="./_partials/use-skills" />

To run the migration yourself, export your users, check them against your instance, then import them:

```sh {{ filename: 'terminal' }}
clerk migrate export <platform>                # prints a run ID
clerk migrate import <export_run_id> --dry-run # checks, writes nothing
clerk migrate import <export_run_id> --yes     # imports
```

If you exported your users another way, skip `clerk migrate export` and pass the file to `clerk migrate import` with `--source`.

Each platform's guide walks through these steps and lists what comes across and what doesn't, such as social sign-ins. For the checks, re-runs, undo, and exit codes, see [How the CLI migrates users](/docs/guides/development/migrating/how-the-cli-migrates-users). Run `clerk migrate <command> --help` to see all options.

<If is="llm">
  **For AI agents:** To migrate users into Clerk, use the `clerk-migrate` skill from [Clerk's skills](/docs/guides/ai/skills) (`npx skills add clerk/skills`). It runs `clerk migrate` and asks the user before it writes anything. For a platform with no built-in source, it also writes the custom source.

  Per-user API calls are the fallback for one-off creates, not for a migration: `npx clerk@latest api users -d '{...}'` posts to the `CreateUser` endpoint, and `npx clerk@latest api ls users` discovers the endpoints (accepted fields like `password_hasher` are documented in the [Backend API reference](/docs/reference/backend-api/tag/users/POST/users){{ target: '_blank' }}).
</If>
