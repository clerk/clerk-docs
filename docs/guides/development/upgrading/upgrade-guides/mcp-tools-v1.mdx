title: Upgrade to `@clerk/mcp-tools` 1.0
description: Learn how to upgrade your MCP server or client from @clerk/mcp-tools 0.9 to 1.0.
---

`@clerk/mcp-tools` 1.0.0 is a breaking release. Every entry point now shares one API, modeled on the Clerk SDKs. Functions drop the `Clerk` suffix. `mcpAuth()`, `withClerkMcpAuth()`, and the metadata handlers share one options object. Each adapter re-exports `@clerk/mcp-tools/server`. The old names are removed, with no deprecated aliases.

> [!IMPORTANT]
> In 1.0, your MCP server is discoverable by default. A client without an access token can connect and list your tools, resources, resource templates, and prompts, with their names, descriptions, and schemas, the protected ones included. Calling them still needs sign-in. In 0.9, every request without a token got a `401`. To keep that behavior, set `discoverable: false`. See [Choose who can list your server](#choose-who-can-list-your-server).

This guide covers each change you need to move from 0.9 to 1.0. To build a new MCP server on 1.0, see [Build and authenticate an MCP server with Clerk](/docs/guides/ai/mcp/build-mcp-server) instead.

## Choose who can list your server

A 1.0 server is discoverable unless you set `discoverable: false`. Clients, directories, and scanners can see what your server offers before anyone signs in, and a call to a tool, resource, or prompt still gets the `401` challenge that starts sign-in. Protected resource metadata and the [Server Card](/docs/guides/ai/mcp/discovery) are public either way.

If your list of tools is a secret, or your tool descriptions or schemas contain anything a client without an account shouldn't read, add `discoverable: false` to the options you pass to `mcpAuth()` or `withClerkMcpAuth()`. Every request then needs a token, as in 0.9:

```ts
const mcpAuthOptions = {
  resourceUrl,
  requiredScopes: ['profile', 'email'],
  discoverable: false,
} satisfies McpAuthOptions
```

In Express, a discoverable server needs `express.json()` mounted before `mcpAuth()`. `mcpAuth()` reads the parsed body to tell a request that lists your tools from one that calls them, and throws a `Clerk error:` for a JSON request without a token when the body isn't parsed. If you can't parse the body first, set `discoverable: false`.

To let clients call some tools, read some resources, or get some prompts without signing in, see [Allow public access to your MCP server before sign-in](/docs/guides/ai/mcp/public-access).

## Issue tokens with an audience

In 1.0, Clerk-verified tokens must have your server's `resourceUrl` as their audience (`aud`), or they get a `401`. Before you upgrade:

1. Ensure your instance issues the `aud` claim. Clerk turns it on when you add the first MCP server to your application in the Clerk Dashboard. If your instance already has MCP servers, follow the steps in [OAuth settings](/docs/guides/ai/mcp/build-mcp-server#oauth-settings) to turn on **Include Audience**. Then reauthorize clients whose tokens have no `aud` claim.
1. Set `resourceUrl` to the full public URL of your MCP endpoint, such as `https://mcp.example.com/mcp`. The examples below read it from the `MCP_RESOURCE_URL` environment variable, so each environment can set its own URL.
1. Have clients send `resource` matching `resourceUrl` when they request a token.

Each auth middleware instance logs a `Clerk warning:` on its first audience rejection. The warning lists these prerequisites and the backend minimum. It doesn't include the token or its claims.

## Update dependencies

1.0 raises the minimum versions of the Clerk SDKs it uses to verify tokens. It also makes the MCP SDK and `zod` optional peers:

- `@clerk/express` 2.1.70, `@clerk/nextjs` 7.9.5, and `@clerk/backend` 3.19.0 are the new minimums. Earlier versions let opaque access tokens, and JWT access tokens without an `aud` claim, pass the audience check.
- `@modelcontextprotocol/sdk` and `zod` are optional peers. List them in your own dependencies if you import the SDK or use `@clerk/mcp-tools/tools`.
- `@modelcontextprotocol/sdk` 1.32.0 and `@modelcontextprotocol/server` 2.3.0 are the new minimums, for upstream security fixes ([GHSA-jm63-cq47-j5jp](https://github.com/advisories/GHSA-jm63-cq47-j5jp), [GHSA-46jr-4wx8-v453](https://github.com/advisories/GHSA-46jr-4wx8-v453), and [GHSA-rvq5-wwqv-78pq](https://github.com/advisories/GHSA-rvq5-wwqv-78pq) affect `@modelcontextprotocol/server` 2.0.0 up to 2.3.0).

## Update your server

`mcpAuth()` in Express and Hono, `withClerkMcpAuth()` in Next.js, and `protectedResourceMetadataHandler()` in all three take the same options object. Define the options once and pass them to both. That way, the metadata's `resource` is the `resourceUrl` that the auth middleware checks, and its `scopes_supported` lists your `requiredScopes`. A token missing any scope in `requiredScopes` gets a `403` `insufficient_scope` challenge.

### Metadata for a non-Clerk authorization server

`protectedResourceHandler({ authServerUrl })` is removed. The adapters' `protectedResourceMetadataHandler()` derives the authorization server from your Clerk Publishable Key. For a non-Clerk authorization server, return `generateProtectedResourceMetadata({ authServerUrl, resourceUrl, properties })` from your own route, with `metadataCorsHeaders`.

By default, `generateProtectedResourceMetadata()` now returns only `resource`, `authorization_servers`, and `bearer_methods_supported: ['header']`. Add other fields through `properties`. Setting `properties.resource` throws.

## Update auth options

`mcpAuth()` and `withClerkMcpAuth()` now check their options at setup, and throw a `Clerk error:` instead of falling through at request time:

- Unknown option keys are rejected, including typos such as `requiredScope` instead of `requiredScopes`.
- A defined `verifyToken` that isn't a function is rejected.
- A `discoverable` that isn't `true` or `false` is rejected. So are `publicAccess.tools`, `resources`, or `prompts` with `discoverable: false`, because no client without a token could connect to reach them.
- Only the Next.js auth and metadata handlers accept `onAuthFailure`. Only the metadata handlers accept `properties`.
- Passing both `clerkClient` and `verifyToken` throws, instead of using the custom verifier and skipping Clerk's audience check. Pass either `clerkClient` with `resourceUrl`, or `verifyToken`.

## Update custom token verifiers

If you pass `verifyToken`, it must follow these rules. Otherwise, the token gets a `401` `invalid_token` challenge:

- Return a finite `expiresAt` and a non-empty `clientId`. A missing, `NaN`, or infinite `expiresAt` gets the cause code `token-claims-missing`, not `token-expired`.
- If you configure `resourceUrl` and your verifier reports a `resource`, the two must match. 0.9 didn't check this. The comparison normalizes letter case in the scheme and host, default ports, and the root path's trailing slash. A trailing slash on any other path must match exactly. A reported `resource` with a fragment is always rejected. For example, the bare origin doesn't match a `resourceUrl` that ends in `/mcp`, and `/mcp/` doesn't match `/mcp`.
- When your JWT library rejects a token, such as with `JWTExpired` from `jose`, catch the error. Then return `undefined` or throw an `McpTokenVerificationError`. Any other error your verifier throws gets a `server_error` response, and the client keeps the token.

`isClerkAuthInfo()` now checks that the library itself created the object. A custom verifier can no longer claim Clerk identity by setting `extra.verifiedBy: 'clerk'`. Hand-built objects, and copies made outside the library, fail the check. To verify Clerk tokens in your own code, replace `verifyClerkToken` with `toClerkAuthInfo(requestState.toAuth(), token)`. Call it only after `authenticateRequest(req, { acceptsToken: 'oauth_token', audience: resourceUrl })`. Never call it on the result of `auth({ acceptsToken: 'oauth_token' })` alone. See [Verify tokens yourself](/docs/guides/ai/mcp/build-mcp-server#verify-tokens-yourself). Otherwise, use `mcpAuth({ clerkClient, resourceUrl })` or `withClerkMcpAuth(handler, { clerkClient, resourceUrl })`.

## Update your MCP client

If you use `@clerk/mcp-tools/client`:

- Reconnect each stored session once with `createKnownCredentialsMcpClient()` or `createDynamicallyRegisteredMcpClient()`. 1.0 binds each session's client credentials to one authorization server. It sends the session's authorization code, client secret, and refresh token only to that server. Sessions stored by an earlier version aren't bound, and neither are sessions with a sign-in in progress during the upgrade. An unbound session keeps its access token until the token is rejected. Its refresh token and client secret aren't sent to any authorization server, and `completeOAuth()` throws for it.
- If your deployment redirects across origins, or redirects in a browser, configure the final MCP endpoint URL. HTTP clients now use the MCP SDK's safer redirect policy.
- If you implement your own `McpClientStore`, consider adding the new optional `compareAndSet(key, expected, value)` method. Without it, the client reads each session and then writes it. That leaves a race when two processes save the same session at once. The Redis, Postgres, and SQLite stores implement it. The file system store, meant for development, doesn't.
