Protections are defenses that Clerk builds and maintains, and that you can turn on for your application. Each one targets a specific kind of abuse, such as sign-ups from cloud servers or disposable email addresses.

## How protections work

- **Each protection applies to specific steps.** Some apply to sign-ups, some to sign-ins, and some to both. A few also apply when a user adds an email address. The **Applies to** column in [Available protections](#available-protections) shows which.
- **Each protection takes one kind of action.** Most block or challenge the attempt. Others reject an email address. The **Action** column shows which.
- **Most are off until you turn them on.** These protections are on by default:
  - [Challenge suspicious sign-ups](/docs/guides/protect/bot-protection) for new applications.
  - [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence) for instances created on or after October 27, 2026.
  - [Require a minimum ClerkJS version](/docs/guides/protect/protections/require-minimum-clerkjs-version) for instances created on or after November 12, 2026.
- **Clerk also rate-limits sign-up and sign-in requests on every plan.** Each IP address can only start so many sign-ups and sign-ins, and submit so many passwords and codes, in a short time. These limits aren't a protection you manage. See [Frontend API requests](/docs/guides/how-clerk-works/system-limits#frontend-api-requests).

## Protections that block or challenge

The guidance below applies to protections that **Block** or **Challenge** an attempt. For protections with other actions, see their individual guides for when they apply and what users see.

### When protections check an attempt

- **Sign-ups through your application are checked.** These protections don't affect existing users' sign-ins, except [Require a minimum ClerkJS version](/docs/guides/protect/protections/require-minimum-clerkjs-version), which checks sign-ins too.
- **Users you create yourself aren't checked.** These protections don't apply to users you create with the [Backend API](/docs/reference/backend-api){{ target: '_blank' }}, in the Clerk Dashboard, or by importing them.
- **Automated tests aren't checked.** A sign-up or sign-in that carries a valid [Testing Token](/docs/guides/development/testing/overview#testing-tokens) isn't checked by these protections, so end-to-end tests keep running.

### What blocked users see

When a protection blocks a sign-up or sign-in, the attempt doesn't go through. What the user sees depends on where it's blocked and which versions of Clerk's SDKs your application runs:

- **Prebuilt components with `@clerk/ui` 1.36.0 or later and ClerkJS 6.34.1 or later** show a screen explaining that the user can't continue, with a reference code. Core 3 SDKs load the latest versions automatically. The screen appears when the attempt is blocked on the first step, or when the user returns from a social or SSO provider.
- **A block at a later step,** such as after the user enters a password or a verification code, shows a short error message instead of the full screen. So do older SDK versions.
- **In a [custom flow](!custom-flow),** the request fails with an error whose code is `action_blocked`. See [Error handling](/docs/guides/development/custom-flows/error-handling).

When a protection challenges an attempt instead, the user completes a verification step and then carries on.

### When more than one protection matches

If more than one protection matches the same attempt, a block applies before a challenge.

### Where decisions appear

Every block and challenge appears as a [Protect event](/docs/guides/dashboard/logs/application-logs#protect-events) in Application Logs, so you can see what a protection is doing once it's on.

### If you proxy Clerk's Frontend API

Several of these protections decide based on where an attempt comes from, so Protect needs each visitor's IP address. If you [proxy Clerk's Frontend API](/docs/guides/dashboard/dns-domains/proxy-fapi) through your own server, your proxy must send the visitor's IP address in the `X-Forwarded-For` header, as described in [Configure your proxy server](/docs/guides/dashboard/dns-domains/proxy-fapi#configure-your-proxy-server). Otherwise every attempt looks like it comes from your proxy, and those protections can block everyone or no one.

## Manage protections in the Dashboard

In the Clerk Dashboard, under **Protect**, navigate to the [**Protections**](https://dashboard.clerk.com/~/protect/protections) page. It has **Basic** and **Advanced** tabs. Basic includes protections on every plan, plus **Block account identifiers** ([Blocklist](/docs/guides/secure/restricting-access#blocklist)) for Pro or higher. Advanced protections require the [Business plan](/pricing).

Protections you can manage show a **Status**. Most have a settings icon. Select it to enable a protection, change its settings, or disable it when supported. **Block account identifiers** has a chevron instead, which opens its page. Each protection is also tagged with what it does, such as **Block**, **Challenge**, or **Rate limit**, and the flows it applies to, **Sign in** or **Sign up**.

Without the Business plan, the **Advanced** tab shows its protections locked: select the lock icon on a protection, or the **Upgrade** button above them, to upgrade. Without the Pro plan, **Block account identifiers** shows an **Upgrade** button instead of opening its page. To test protections before you enable them in production, see [Enable protections](/docs/guides/protect/getting-started#enable-protections).
