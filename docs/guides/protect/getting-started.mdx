title: Get started with Protect
description: Check that your application meets Clerk Protect's requirements, then enable protections in the Clerk Dashboard.
---

Before you enable protections on the **Protections** page, your application must meet the following requirements.

## Requirements

- **ClerkJS 6.39.0 or later** - Clerk's SDKs load the latest version by default. If you bundle or host `@clerk/clerk-js` yourself, update it. To check your version, run `window.Clerk.version` in your browser's console.
- **Content Security Policy** - If your application sets one, add [Clerk's CSP headers](/docs/guides/secure/best-practices/csp-headers).
- **Custom flows** - If your application uses custom authentication flows, they need to handle new error messages and [display challenges](/docs/guides/development/custom-flows/authentication/bot-sign-up-protection).
- **Current bot protection** - Older applications might use legacy bot sign-up protection and need to [update to **Challenge suspicious sign-ups**](/docs/guides/secure/legacy-bot-protection#update-to-challenge-suspicious-sign-ups).

## Enable protections

In the Clerk Dashboard, navigate to [**Protections**](https://dashboard.clerk.com/~/protect/protections) or [**Sign-in security**](https://dashboard.clerk.com/~/protect/sign-in-security) under **Protect**, depending on the protection you want to configure. See [Protections](/docs/guides/protect/protections/overview) or [Sign-in security](/docs/guides/protect/sign-in-security/overview) for a description of what each page offers.

Each instance has separate protection settings. For protections on the **Protections** page, test the sign-up and sign-in flows they affect in development without a [Testing Token](#bypass-protections-in-tests), review any Protect events in [Application Logs](/docs/guides/dashboard/logs/application-logs#protect-events), then use the same settings in your production instance.

> [!WARNING]
> Instances created on or after October 27, 2026 start with [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence#if-its-already-on) on. The **Protections** page shows it as enabled even if your application doesn't meet the requirements above. If an older ClerkJS or your Content Security Policy prevents Device Intelligence from running, every browser sign-up without a Testing Token is blocked. Test a sign-up without one in each new instance.
>
> Instances created on or after November 12, 2026 also start with [Require a minimum ClerkJS version](/docs/guides/protect/protections/require-minimum-clerkjs-version#if-its-already-on) enabled. It blocks browser sign-ups and sign-ins below its configured ClerkJS minimum. The default minimum is 6.42.3, which blocks every app on a Core 2 SDK.

## Native API considerations

Clerk's native SDKs for iOS, Android, and Expo require the Native API to be enabled and don't support challenges yet.

- **Protections configured to challenge** will allow attempts from native environments without a challenge.
- **Protections configured to block** still apply to native environments.
- **[Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence)** and **[Require a minimum ClerkJS version](/docs/guides/protect/protections/require-minimum-clerkjs-version)** apply to browsers only, so native environments skip them.

Because the Native API is public, attackers can also use it to bypass challenge-based protections. Only enable it if your application requires it. When the Native API is disabled, Clerk rejects requests from native applications with a `native_api_disabled` error.

## Bypass protections in tests

[Testing Tokens](/docs/guides/development/testing/overview#testing-tokens) let automated tests skip the protections that block or challenge. That includes [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence), so a browser test that uses one isn't blocked when it can't run Device Intelligence.
