description: Check that your application meets Clerk Protect's requirements, then enable protections in the Clerk Dashboard.

Before you can enable protections, your application must meet the following requirements.

## Requirements

- **ClerkJS 6.39.0 or later** - Clerk's SDKs load the latest version by default. If you bundle or host `@clerk/clerk-js` yourself, update it. To check your version, run `window.Clerk.version` in your browser's console.
- **Content Security Policy** - If your application sets one, add [Clerk's CSP headers](/docs/guides/secure/best-practices/csp-headers).
- **Custom flows** - If your application uses custom authentication flows, they need to handle new error messages and [display challenges](/docs/guides/development/custom-flows/authentication/bot-sign-up-protection).
- **Current bot protection** - Older applications might use legacy bot sign-up protection and need to [update to **Challenge suspicious sign-ups**](/docs/guides/secure/legacy-bot-protection#update-to-challenge-suspicious-sign-ups).

## Enable protections

Navigate to the [**Protections**](https://dashboard.clerk.com/~/protect/protections) page in the Clerk Dashboard to configure each protection. See [Protections](/docs/guides/protect/protections/overview) for a description of what each one does.

Each instance has separate protection settings. Test sign-ups in development without a [Testing Token](#bypass-protections-in-tests), review any Protect events in [Application Logs](/docs/guides/dashboard/logs/application-logs#protect-events), then enable the same protections in your production instance.

Instances created on or after October 27, 2026 start with [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence#if-its-already-on) on, and the **Protections** page shows it as enabled whether or not your application meets the requirements above. When Device Intelligence can't run, for example because of an older ClerkJS or a Content Security Policy that blocks it, the protection blocks every browser sign-up without a Testing Token. In each new instance, sign up from a browser without one to check.

## Native API considerations

Clerk's native SDKs for iOS, Android, and Expo require the Native API to be enabled and don't support challenges yet.

- **Protections configured to challenge** will allow attempts from native environments without a challenge.
- **Protections configured to block** still apply to native environments.
- **[Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence)** applies to browsers only, so native environments skip it.

Because the Native API is public, attackers can also use it to bypass challenge-based protections. Only enable it if your application requires it. When the Native API is disabled, Clerk rejects requests from native applications with a `native_api_disabled` error.

## Bypass protections in tests

[Testing Tokens](/docs/guides/development/testing/overview#testing-tokens) let automated tests skip the protections that block or challenge. That includes [Require Device Intelligence checks](/docs/guides/protect/protections/require-device-intelligence), so a browser test that uses one isn't blocked when it can't run Device Intelligence.
